# Microsoft Foundry Standard·Flex 비교 실험

## 1. Flex란?

Flex는 Microsoft Foundry에서 지원하는 저우선순위 추론 처리 옵션이다. **입력·출력 토큰 단가는 Standard 대비 50% 할인**되지만, 응답시간이 길어지거나 처리 용량이 일시적으로 부족할 수 있다. 지연에 여유가 있는 분석, 평가, 데이터 가공 등의 작업에 적합하다.

별도의 Flex 배포를 만드는 방식은 아니다. 같은 Global Standard 배포에 요청하면서 `service_tier`를 `flex`로 지정하면 된다. Standard 요청은 `default`를 사용한다.

현재 프리뷰이며, **지연시간·서비스 SLA는 제공하지 않는다.** 따라서 비용 절감과 함께 응답시간의 변동성을 고려해야 한다.

### 사용하기 적합한 경우

**사용자가 결과를 즉시 기다리지 않고, 대기나 재시도를 허용할 수 있으며, 비용 절감이 중요한 작업**에 적합하다.

| 유형 | 활용 예시 |
| --- | --- |
| 문서 요약·분석 | 저장된 회의록, 보고서, 문서를 모아서 요약하거나 핵심 항목을 추출 |
| 데이터 분류·정보 보강 | 수집한 문서에 태그를 붙이거나, 문의 내용을 분류하고 JSON 형태로 정보 추출 |
| 모델·프롬프트 평가 | 여러 모델과 프롬프트 조합을 반복 실행해 답변 정확도나 출력 형식을 평가 |
| 비동기 백그라운드 생성 | 작업 큐에서 보고서·콘텐츠 초안을 생성하고, 완료되면 사용자에게 별도로 알림 |

반대로 **실시간 고객 응대나 온라인 화면의 응답 경로처럼 일정한 응답시간이 필요한 작업**에는 우선 선택으로 적합하지 않다. 평균 응답이 빠르더라도 **tail latency**나 일시적인 용량 부족으로 사용자가 오래 기다릴 수 있기 때문이다.

적용 시에는 업무별 허용 대기시간과 재시도 횟수를 정해야 한다. 완료를 우선해야 하는 작업은 Flex 용량 부족 시 Standard로 재요청하는 정책도 검토할 수 있지만, 이는 애플리케이션에서 구현해야 하는 폴백이지 자동 전환 기능은 아니다.

근거: [Microsoft 공식 처리 옵션 선택 안내](https://learn.microsoft.com/azure/foundry/openai/how-to/flex-processing#choose-a-processing-option)

### Batch와 비교했을 때의 장점과 선택 기준

여기서 Batch는 Azure OpenAI의 **Global Batch**를 뜻한다. Flex와 Batch는 모두 Standard 대비 50% 할인된 단가를 제공하므로, **Flex의 장점은 더 낮은 가격보다는 기존 개별 API 호출 방식을 유지할 수 있다는 점**에 있다. 아래는 처리 방식의 비교이며, 이번 실험에서 Batch의 성능을 측정한 것은 아니다.

| 항목 | Flex | Global Batch |
| --- | --- | --- |
| 요청·결과 처리 | 개별 API 요청의 응답으로 결과 수신 | 요청 파일 제출, 배치 작업 생성, 상태 확인 후 결과 파일 회수 |
| 배포 | 기존 Global Standard 배포 사용 | Global Batch 배포 사용 |
| 처리 시간 | 개별 요청의 응답시간이 변동하며 지연시간 SLA 없음 | 24시간 내 완료를 목표로 하지만 더 오래 걸릴 수 있음 |
| 쿼터 | 해당 Global Standard 배포의 쿼터와 공유 | 별도 enqueued token 쿼터 사용 |

#### Flex가 더 편한 경우

- **수시로 들어오는 개별 작업:** 문서 하나가 등록되면 요약하는 식의 처리에 요청 파일과 배치 작업을 매번 만들 필요가 없다.
- **기존 애플리케이션에 최소한의 변경으로 적용:** 지원 모델의 기존 요청에 `service_tier="flex"`를 지정하면 되므로 파일 업로드·작업 상태 확인·결과 회수 절차를 추가하지 않아도 된다.
- **앞 단계 결과로 다음 요청이 정해지는 작업:** 정보 추출 결과를 받아 요약이나 보고서 생성을 이어가는 흐름에 연결하기 쉽다.
- **요청별 Standard 폴백 정책:** Flex 용량 부족 시 같은 요청을 `default`로 재요청하는 경로를 구성하기 쉽다. Batch도 실패 항목을 Standard로 처리할 수 있지만, 결과에서 실패 항목을 찾아 연결하는 절차가 필요하다. 둘 다 자동 폴백은 아니다.

#### Batch가 더 적합한 경우

- **이미 모인 대량의 독립된 작업:** 서로의 결과에 의존하지 않는 문서 분석이나 데이터 분류를 한꺼번에 제출할 수 있다.
- **결과를 즉시 회수하지 않아도 되는 일괄 처리:** 요청마다 응답을 받아 다음 단계를 진행할 필요가 없고, 작업 결과를 모아서 처리해도 되는 경우다.
- **온라인 요청과 쿼터를 분리해야 하는 작업:** 대량 오프라인 처리를 별도 enqueued token 쿼터로 운영할 수 있다. Flex는 같은 배포의 Standard 쿼터를 공유하므로 이 목적의 대안은 아니다.

Batch의 24시간은 완료 목표이지, 반드시 그만큼 기다린다는 뜻도 완료를 보장한다는 뜻도 아니다. Flex 역시 **tail latency**를 고려해야 하므로, 엄격한 응답시간이 필요한 작업은 둘 중 하나를 선택하기보다 Standard·Priority·프로비저닝 처리 등 다른 옵션을 검토하는 편이 적절하다.

정리하면 **대량 오프라인 일괄 처리에는 Batch, 수시로 들어오는 개별 백그라운드 작업에는 Flex**가 자연스럽다. 실제 선택은 지원 모델, 처리량, 완료 기한과 기존 처리 흐름에 따라 달라진다.

근거: [Flex 처리 옵션](https://learn.microsoft.com/azure/foundry/openai/how-to/flex-processing#choose-a-processing-option), [Azure OpenAI Global Batch](https://learn.microsoft.com/azure/foundry/openai/how-to/batch)

## 2. 실험 방법

- **모델:** `gpt-6-sol`, `gpt-6-luna`
- **프롬프트:** 네트워크 설명, 회의록 요약, JSON 추출, 수리 문제, 코드 작성의 5개
- **방식:** 같은 프롬프트를 두 모델 × 두 티어의 4개 조합에 동시에 요청하고, 모두 끝나면 10초 대기
- **횟수:** 다섯 프롬프트를 번갈아 실행하며 각각 10회 반복. 총 50회 시행, 200개 요청
- **측정:** 전체 응답 완료 시간, 성공 여부, 실제 처리 티어, 토큰 사용량과 오류를 저장. 자동 재시도나 Standard 폴백은 사용하지 않음

## 3. 결론

**이번 실험에서는 Flex도 지연에 여유가 있는 작업에 활용을 검토할 만한 응답속도를 보였다. 다만 “Flex가 Standard보다 빠르다”거나 “항상 비슷한 속도를 제공한다”는 결론을 내릴 수는 없다.**

성공한 요청의 전체 응답 완료 시간을 비교하면 다음과 같다.

| 모델 | Standard 평균 | Flex 평균 | Standard 최대 | Flex 최대 |
| --- | ---: | ---: | ---: | ---: |
| `gpt-6-sol` | 3.48초 | 4.15초 | 6.03초 | 17.57초 |
| `gpt-6-luna` | 3.56초 | 2.82초 | 7.15초 | 5.84초 |

각 모델·티어의 성공 요청 49~50개를 집계한 값이다. 첫 토큰 도착 시간이 아니라 전체 응답을 받기까지의 시간이다.

### 응답속도는 활용을 검토할 만하지만, tail latency를 고려해야 한다

평균적으로는 두 모델의 Flex 모두 수 초 안에 응답했다. Luna에서는 Flex가 더 빨랐지만, Sol에서는 더 느렸다. 모델에 따라 결과가 달랐으므로 속도 우열보다는 **비용을 줄이면서 수용 가능한 응답성을 확보할 수 있는지**에 초점을 맞추는 것이 적절하다.

특히 Sol Flex에서는 **17.57초의 응답이 관측됐다.** 평균이 짧더라도 일부 요청이 오래 걸리는 **tail latency**가 있을 수 있다. 운영 적용 시에는 평균뿐 아니라 상위 지연시간과 최대 응답시간을 확인하고, 업무별 허용 대기시간을 정해야 한다.

### 이번 실패를 Flex의 용량 부족으로 해석할 수는 없다

전체 요청 중 198개가 성공했고, Standard와 Flex는 각각 100개 중 99개가 성공했다. 실패 2건은 두 티어에서 각각 발생한 이름 해석 오류(`APIConnectionError`)였으며, Flex 용량 부족을 나타내는 HTTP 429는 관찰되지 않았다.

따라서 이번 결과만으로 티어별 가용성 차이나 Flex 용량 부족 시의 동작을 판단할 수는 없다. Flex 실패 후 Standard로 재요청하는 폴백 경로도 이번 실험에서는 검증하지 않았다.

### 비용 절감 후보로는 긍정적이지만, 운영 조건에 맞는 추가 검증이 필요하다

공식 단가 기준으로는 약 50%의 비용 절감 여지가 있다. 다만 실제 청구 금액을 확인한 실험은 아니며, 요청마다 출력 토큰 수가 달라 작업당 비용이 정확히 절반이 된다고 보장할 수는 없다.

**지연에 여유가 있는 비동기·백그라운드 작업에는 Flex 우선 적용을 검토할 만하다.** 반면 엄격한 응답시간이 필요한 작업은 신중하게 판단해야 한다. 짧은 프롬프트와 동시 요청 4개로 수행한 소규모 실험이므로, 긴 입력·높은 동시성·혼잡 상황에서도 같은 결과가 나온다고 일반화해서는 안 된다.
