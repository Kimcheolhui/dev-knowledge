# mTLS와 워크로드 신원

별도 세션. [certificate](../certificate/README.md)가 다뢬 것은 도메인 이름 기반의 **서버 인증서**다. 클라이언트가 서버를 검증하는 단방향 구조이고, 신뢰의 근거는 공인 CA와 OS·브라우저의 신뢰 저장소다.

이 세션은 그 모델이 성립하지 않는 영역을 다룬다. 워크로드끼리 서로를 인증해야 하고, 식별자로 쓸 안정적인 도메인 이름이 없으며, 신뢰 경계가 네트워크 위치가 아니라 워크로드 자체인 경우다.

이 세션은 진행 중이다. 현재는 2장만 작성되어 있고, 1장과 3장은 아래 개요를 기준으로 학습하며 채운다.

|---|---|---|
| 1. mTLS | `01_mtls.md` | 작성 예정 |
| 2. SPIFFE와 SPIRE | [02_spiffe-and-spire.md](02_spiffe-and-spire.md) | 작성됨 |

## 1. mTLS

프로토콜 계층. 단방향 TLS와 무엇이 달라지는지부터 시작한다.

- 핸드셰이크의 변화: `CertificateRequest`, 클라이언트의 `Certificate`와 `CertificateVerify`
- 클라이언트 인증서의 요건. EKU가 `clientAuth`여야 하는 이유
- 검증 주체와 신뢰 앵커. 서버가 어떤 CA를 신뢰하도록 설정하는가
- 종료 지점의 문제. LB나 게이트웨이에서 TLS를 끊으면 클라이언트 인증서 정보가 어떻게 전달되는가
- 운영 부담: 클라이언트 쪽 인증서의 배포·갱신·폐기. 여기서 3장과 이어진다

`certificate` 세션의 3-3에서 프로토콜 수준의 양방향 인증을 이미 다룬다. 이 장은 그 내용을 반복하지 않고 운영 관점에서 이어받는다.

## 2. SPIFFE와 SPIRE

신원 계층. mTLS를 실제로 운영할 때 남는 문제, 즉 "누구에게 어떤 인증서를 어떻게 주는가"를 다룬다.

- 등장 배경: 워크로드에 안정적인 이름이 없다, 자격 증명 배포의 부트스트랩 순환, 신뢰 경계의 이동
- SPIFFE ID, SVID, Workload API
- SPIRE의 노드 인증과 워크로드 인증, 페더레이션
- cert-manager와의 역할 구분

## 3. 서비스 메시

적용 계층. 앞의 두 장을 애플리케이션 수정 없이 적용하는 방식이다.

- 사이드카와 앰비언트. 데이터 플레인의 위치에 따른 차이
- 메시가 제공하는 워크로드 신원. Istio가 SPIFFE ID 형식을 쓰는 이유
- 인증서 발급과 회전을 메시가 대신하는 구조. 컨트롤 플레인의 CA
- `PeerAuthentication`, `AuthorizationPolicy` — 인증과 인가의 분리
- eBPF 기반 구현과의 비교. [cilium](../../cilium/cilium-session.md) 문서와 연결
- 도입 판단: 메시 없이 SPIRE만 쓰는 경우, 메시만으로 충분한 경우
