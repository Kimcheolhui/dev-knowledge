## 1. cert-manager (12분)

### 1-1. cert-manager 개요

- X.509 인증서의 발급과 갱신을 자동화하는 쿠버네티스 컨트롤러
- Jetstack이 kube-lego의 후속으로 시작했고 이후 CNCF Graduated
- 발급 주체를 추상화한다. 어디서 발급받든 사용하는 쪽 인터페이스는 동일한 `Secret`
- 담당 범위는 발급과 갱신. 트래픽에 적용하는 일은 하지 않는다

### 1-2. 등장 배경

- 인증서에는 수명이 있고, 수동 교체는 만료 감시 주체 부재・수작업・인계 누락 문제를 남긴다
- 수명 단축 추세 (CA/Browser Forum SC-081v3: 2026년 200일 → 2027년 100일 → 2029년 47일)
- 단축의 이유는 폐기 메커니즘이 실효성 있게 동작하지 않기 때문
- 종합: 갱신 주기 단축 × 관리 대상 수 증가 × 인프라 가변성이 겹쳐 작업량이 곱으로 늘어난다. 셋 중 하나만이었다면 자동화가 필수는 아니었다
- 쿠버네티스의 선언적 모델과 결합: 선언하면 컨트롤러가 그 상태로 수렴시킨다

### 1-3. 구성 요소

개념(인증서, 인증기관)과 쿠버네티스 리소스의 대응 관계로 설명한다.

| 개념 | 리소스 | 생성 주체 |
|---|---|---|
| 인증기관 | `Issuer` / `ClusterIssuer` | 사용자 |
| 필요한 인증서 | `Certificate` | 사용자 (또는 ingress-shim) |
| 발급 요청 | `CertificateRequest` | cert-manager |
| 소유권 검증 | `Order` / `Challenge` | cert-manager |
| 결과물 | `Secret` (`kubernetes.io/tls`) | cert-manager |

- Issuer 타입: ACME, CA, SelfSigned
- 공인 CA와 사내 CA의 차이는 발급 능력이 아니라 신뢰 범위
- ingress-shim: Ingress나 Gateway에 어노테이션만 달면 `Certificate`가 자동 생성되는 경로

### 1-4. 발급 과정과 도메인 소유권 검증

개인키·CSR 생성 → 발급 주체에 따라 분기 → 소유권 검증 → 서명된 인증서 → `Secret` 생성·갱신

- 도메인 소유권 검증이 ACME 발급의 실질적인 관문
  - HTTP-01: 지정된 경로에 토큰을 응답. 80 포트 노출 필요, 와일드카드 불가
  - DNS-01: TXT 레코드를 등록. 존 쓰기 권한 필요, 와일드카드 가능, 내부 전용 서비스에도 사용 가능
- 갱신: 만료 전 일정 시점에 위 과정 전체를 다시 수행

### 1-5. cert-manager의 역할이 아닌 것

- TLS 종료 자체 — Ingress Controller, Gateway, LB의 영역 (3-4로 연결)
- 갱신된 Secret을 애플리케이션이 다시 읽게 만드는 것 — 파드 재시작이나 앱의 리로드가 필요
- 클라이언트 신뢰 저장소에 Root CA를 배포하는 것
- mTLS 검증 정책 강제 — 앱이나 메시의 영역
- Secret의 암호화 저장

## 2. 인증서와 인증기관 (10분)

### 2-1. 등장 배경

- 공개키만으로는 "이 공개키가 정말 그 도메인의 것인가"를 알 수 없다. 중간자가 자신의 공개키를 대신 넘겨도 구분되지 않는다
- 신뢰할 수 있는 제3자가 "이 공개키는 이 도메인의 것"이라고 보증하는 문서가 인증서
- Root CA가 모든 도메인을 직접 서명하지 않는 이유: Root 개인키를 온라인에 두면 유출 시 전체 신뢰가 무너진다. 그래서 오프라인에 격리하고 중간 CA에 서명 권한을 위임

### 2-2. 인증서에 담긴 것

- SAN: 이 인증서가 유효한 도메인 목록. CN은 사실상 사용되지 않는다
- 발급자(Issuer), 공개키, 유효기간
- Basic Constraints: `CA:TRUE` 이면 다른 인증서를 서명할 수 있다
- Key Usage / EKU: `serverAuth`, `clientAuth`
- 발급자의 서명
- 예시: `openssl x509 -text`로 서버 인증서 / 중간 CA / Root CA 비교

### 2-3. 신뢰 체인

`app.example.com` 인증서 → 중간 CA 인증서 → Root CA 인증서

- 서명과 검증: 인증서 본문 전체의 해시를 상위 CA의 개인키로 서명하고, 클라이언트는 상위 CA의 공개키로 그 서명을 검증한다
- `app.example.com`을 신뢰하는 과정: 상위로 한 단계씩 올라가며 서명을 확인
- Root CA를 신뢰하는 이유: Root는 검증 대상이 아니라 신뢰의 출발점이다. self-signed이며, OS와 브라우저의 신뢰 저장소에 사전 배포되어 있다
- 서버가 전송해야 하는 것: 서버 인증서 + 중간 CA. 누락 시 클라이언트에 따라 결과가 갈린다(AIA)
- 서명 외 확인 항목: 유효기간, 호스트명, 용도, CA 여부, 폐기
- 폐기 확인(CRL·OCSP)의 구조적 한계와, 그래서 수명 단축으로 간 배경

## 3. TLS (12분)

### 3-1. TLS 1.2 → 1.3

- TLS가 제공하는 것: 기밀성, 무결성, 인증
- 핸드셰이크(대칭키 합의)와 레코드(데이터 암호화)의 분리
- 1.2의 문제
  - 핸드셰이크 2-RTT. 연결 수립 지연
  - 취약한 알고리즘이 협상 대상에 남아 있었다 (RC4, CBC 계열, RSA 키 교환)
  - RSA 키 교환은 전방향 안전성(PFS)이 없다. 서버 개인키가 유출되면 과거에 수집된 트래픽까지 복호화된다
  - 협상 과정을 조작한 다운그레이드 공격이 가능했다
  - 인증서가 평문으로 전송된다
- 1.3의 변경
  - key share 선제 전송으로 1-RTT
  - 취약 알고리즘 제거, cipher suite 5개로 축소
  - PFS 강제
  - 인증서 전송 구간이 암호화된다
  - transcript 서명으로 다운그레이드 차단

### 3-2. SNI

- 배경: 하나의 IP에 여러 도메인. 인증서는 `Host` 헤더를 읽기 전에 골라야 한다
- 클라이언트가 접속하려는 호스트명을 ClientHello에 실어 보내는 확장
- Ingress Controller가 여러 `Secret` 중 하나를 고르는 기준
- SNI 없이 접속하면 기본 인증서가 반환된다. SNI와 `Host` 헤더가 갈리면 인증서와 라우팅 기준이 달라진다
- TLS 1.3에서도 평문. 프라이버시 측면의 한계와 ECH

### 3-3. mTLS

- 배경: 애플리케이션 계층 인증의 한계, 내부망을 신뢰하는 전제의 붕괴
- 추가되는 메시지: `CertificateRequest`, `Certificate`, `CertificateVerify`
- 서버 인증과의 비대칭: 대조할 이름이 없다 → 인증(TLS)과 인가(앱)의 분리
- 클라이언트 인증서는 사내 CA로 발급해야 한다
- 서비스 메시의 자동 mTLS와 SPIFFE ID

### 3-4. TLS 종료 지점

응용 수준에서 실제로 결정해야 하는 지점. 인증서를 어디에 둘지가 여기서 갈린다.

| 방식 | 복호화 지점 | 백엔드 구간 | 인증서가 필요한 곳 |
|---|---|---|---|
| Edge 종료 | LB·Ingress | 평문 | LB·Ingress |
| Re-encrypt | LB·Ingress에서 한 번, 파드에서 다시 | 암호화 | LB·Ingress + 파드 |
| Passthrough | 파드 | 암호화 | 파드 |

- cert-manager가 만든 `Secret`을 누가 소비하는지가 방식에 따라 달라진다
- Passthrough는 SNI만 보고 라우팅하므로 경로 기반 라우팅이나 헤더 조작 같은 L7 기능을 쓸 수 없다
- mTLS 검증도 복호화가 일어나는 지점에서 수행된다

## 4. Let's Encrypt와 nip.io (3분)

앞에서 설명한 구조 안에서 각각이 어느 자리를 차지하는지만 다룬다.

### Let's Encrypt

- 위치: 2장의 인증기관, 1장의 `Issuer`가 바라보는 대상
- 배경: 인증서 발급이 유료이고 수동이던 시절에는 HTTPS 적용 자체가 비용이었다. 무료·자동 발급으로 그 장벽을 제거
- 제공하는 것: ACME 프로토콜 기반 자동 발급. 도메인 소유권 검증을 자동화한 것이 핵심
- 특징: 도메인 소유권만 검증(DV). 짧은 수명을 전제로 자동 갱신을 강제
- 쓰임: cert-manager의 ACME Issuer 대상으로 지정. 운영 적용 전에는 staging 엔드포인트로 먼저 검증

### nip.io

- 위치: 2장의 SAN에 들어갈 도메인을 확보하는 수단
- 배경: 검증이나 실습에 공인 인증서가 필요한데, 도메인 등록과 DNS 설정은 부담
- 제공하는 것: 와일드카드 DNS. `<IP>.nip.io` 형태의 이름을 해당 IP로 응답
- 쓰임: 퍼블릭 IP만 있으면 도메인처럼 쓸 수 있어 HTTP-01 검증이 성립한다. 실습·테스트 용도 한정

## 5. 인증서로 인한 장애 사례 (3분)

앞에서 설명한 메커니즘과 연결해서 실제 사례로.

- Ericsson(2018) — 제품에 포함된 인증서 만료로 11개국 이동통신 데이터 중단 (1-2)
- 중간 CA 누락 — 클라이언트마다 결과가 갈린다 (2-3)
- `Secret`은 갱신됐지만 앱이 옛 인증서를 계속 서빙 — cert-manager의 범위 밖 (1-5)
- 증상으로 역추적하는 표
- 유효기간 단축이 만드는 앞으로의 위험
