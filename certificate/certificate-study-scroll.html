Overview

다루는 범위와 순서

도구(cert-manager) → 산출물(인증서·CA) → 그것이 쓰이는 프로토콜(TLS) → 실제 발급처(Let's Encrypt) → 무너졌을 때(장애 사례) 순서로 내려갑니다.

1. cert-manager

선언하면 인증서를 발급·갱신해 Secret에 넣어 두는 쿠버네티스 컨트롤러. 그리고 어디까지가 담당이 아닌지.

2. 인증서와 인증기관

왜 제3자(CA)가 필요한가, 인증서에는 무엇이 담기는가, 신뢰 체인은 어떻게 검증되는가.

3. TLS

TLS 1.2 → 1.3의 변화, SNI, mTLS, 그리고 실제로 결정해야 하는 TLS 종료 지점.

4. Let's Encrypt와 nip.io

무료·자동 발급이 가능해진 배경과, 도메인 없이 실습 환경을 만드는 방법.

5. 장애 사례

실제로 무엇이 터졌는가. 공통점은 발급 실패가 아니라 발급 이후를 추적하는 주체의 부재.

전제

암호학 내부 구현, 프로토콜 바이트 단위 분석은 범위 밖입니다. 운영에서 판단이 갈리는 지점 위주로 봅니다.

1-1 · cert-manager

cert-manager 개요

쿠버네티스에서 X.509 인증서의 발급과 갱신을 자동화하는 컨트롤러입니다.

담당 범위

인증서 수명 주기 중 발급과 갱신. 발급된 인증서를 트래픽에 적용하는 일은 하지 않습니다.

X.509

공개키 인증서의 형식을 정의한 표준(RFC 5280). 인증서에 어떤 항목이 어떤 구조로 들어가는지를 규정합니다. 주체(도메인), 공개키, 발급자, 유효기간, 발급자의 서명 등이 포함됩니다. TLS/HTTPS에서 쓰는 인증서는 모두 X.509 형식입니다. 상세는 2장에서 다룹니다.

프로젝트 배경

2017년 Jetstack이 kube-lego의 후속으로 시작했고, CNCF에 기부되어 2024년 Graduated 단계에 올랐습니다. 쿠버네티스 환경의 인증서 관리에서 사실상 표준입니다.

동작 방식

CRD로 "필요한 인증서"를 선언하면 컨트롤러가 발급 과정을 수행하고 결과를 Secret으로 만들어 둡니다. 만료가 가까워지면 같은 과정을 다시 수행합니다.

Jetstack

영국의 쿠버네티스 전문 회사(2015년 설립). cert-manager를 만들어 오픈소스로 공개했습니다. 2020년 Venafi에 인수됐고, Venafi는 2024년 CyberArk에 인수됐습니다. 프로젝트 자체는 CNCF 소유라 특정 벤더에 종속되지 않습니다.

kube-lego

Jetstack이 2016년에 만든 프로젝트. 쿠버네티스 Ingress에 Let's Encrypt 인증서를 자동으로 붙이는 역할만 했습니다. Let's Encrypt와 nginx Ingress에만 동작하고 발급 주체를 바꿀 수 없는 구조라, cert-manager가 이를 일반화하면서 2018년 보관 종료됐습니다.

1-2 · Why

등장 배경

인증서에는 수명이 있고, 그 수명이 계속 짧아지고 있습니다. 자동화가 선택이 아니라 전제가 된 이유입니다.

한 줄

만료되면 클라이언트는 접속을 거부합니다. 인증서를 쓰는 서비스라면 주기적인 교체가 반드시 필요합니다.

수동 관리의 한계

감시 주체 부재

만료를 추적하는 주체가 없고 달력이나 개인 메모에 의존합니다.

절차의 비표준

발급·파일 배포·리로드가 각각 수동이고 절차가 서비스마다 다릅니다.

인계 누락

담당자가 바뀌면 절차와 만료일 정보가 함께 사라집니다.

이 방식은 인증서 수가 적고 수명이 길 때만 유지됩니다.

수명 단축 추세

공인 인증서의 최대 유효기간은 계속 줄어왔습니다. Baseline Requirements 초기에는 60개월이었고, 이후 39개월 → 825일 → 398일로 줄었습니다. Let's Encrypt는 처음부터 90일을 채택했습니다.

CA/Browser Forum

인증기관(CA)과 브라우저·OS 벤더가 참여하는 협의체(2005년 발족). 공인 인증서의 발급 기준인 Baseline Requirements를 관리합니다. ISO나 IETF 같은 공식 표준화 기구는 아니고 법적 강제력도 없지만, Chrome·Firefox·Apple·Microsoft의 루트 프로그램이 "BR 준수"를 신뢰 저장소 등재 조건으로 걸기 때문에 사실상 강제됩니다. 위반한 CA는 신뢰 저장소에서 제거됩니다.

왜 짧아지나: 폐기(revocation) 메커니즘이 실효성 있게 동작하지 않기 때문입니다. 유출된 인증서를 확실히 무효화할 방법이 마땅치 않으니, 대신 인증서 자체를 빨리 만료시키는 쪽을 택했습니다. 구체적인 이유는 2-3에서 다룹니다.

쿠버네티스와 마이크로서비스가 더한 것

관리 대상 수의 증가

서비스마다 도메인이 생기고, 내부 통신까지 TLS로 감싸면 인증서 수는 서비스 수만큼 늘어납니다.

인프라의 가변성

파드는 수시로 생성되고 사라집니다. 특정 서버에 인증서 파일을 올려두는 모델이 성립하지 않습니다.

왜 자동화가 아니면 안 되는가

지금까지 본 것을 합치면 세 가지 변화가 같은 시기에 겹쳤습니다.

축 변화 작업량에 미치는 영향
갱신 주기 398일 → 200일 → 47일 인증서 하나당 연 1회에서 연 8회로
관리 대상 수 서비스마다 도메인, 내부 통신까지 TLS 인증서 수가 서비스 수만큼 늘어남
대상의 가변성 파드는 수시로 생성·소멸 특정 서버에 파일을 두는 모델이 성립하지 않음

작업량은 인증서 수 × 연간 갱신 횟수로 늘어납니다. 서비스 30개에 47일 인증서면 연 240회입니다. 사람이 달력으로 관리할 수 있는 규모가 아닙니다.

셋 중 하나만 있었다면 자동화가 필수는 아니었습니다. 인증서가 한 장뿐이면 47일 주기도 감당할 수 있고, 수명이 2년이면 서비스가 많아도 버틸 수 있으며, 서버가 고정되어 있으면 파일을 올려두는 방식이 통합니다. 세 가지가 겹쳤기 때문에 자동화가 선택이 아니라 전제가 됐습니다.

선언적 모델로의 전환

선언: 이 도메인의 유효한 인증서가 이 Secret에 존재해야 한다 → 수렴: 없으면 발급하고, 만료가 가까우면 갱신한다. cert-manager는 이 수렴 루프를 담당하는 컨트롤러입니다.

Issuer / ClusterIssuer

인증서를 어디서 발급받을지를 정의합니다. 둘의 차이는 유효 범위뿐이고 스펙은 동일합니다.

  • Issuer: 네임스페이스 범위. 같은 네임스페이스의 Certificate만 참조할 수 있습니다
  • ClusterIssuer: 클러스터 범위. 참조하는 Secret(ACME 계정 키, CA 키 등)은 cert-manager가 설치된 네임스페이스에서 찾습니다
타입 발급 주체 용도
acme Let's Encrypt 등 ACME 지원 CA 공인 인증서. 외부에 노출되는 도메인
ca 클러스터 내 Secret에 보관된 CA 키·인증서 사내 인증서, mTLS
selfSigned 없음. 자기 자신이 서명 테스트, 사내 Root CA를 만들 때의 시작점
vault, venafi 외부 인증서 관리 시스템 별도 인프라가 있는 경우

vault는 Azure Key Vault가 아닙니다. 여기서 vault는 HashiCorp Vault의 PKI 시크릿 엔진을 가리킵니다. cert-manager에는 Azure Key Vault용 내장 Issuer 타입이 없습니다. Key Vault는 통합 CA(DigiCert, GlobalSign)로 자체적으로 발급・갱신까지 수행하므로 cert-manager의 백엔드가 아니라 대안에 가깝습니다. 쿠버네티스에서 쓰려면 Secrets Store CSI Driver로 Secret을 동기화하거나 AKS app routing add-on의 어노테이션을 씁니다. 둘 다 cert-manager 경로가 아닙니다.

마찬가지로 1-4의 DNS-01 예시에 나오는 azureDNS도 Issuer 타입이 아니라 solver입니다. 발급은 Let's Encrypt가 하고 Azure DNS는 TXT 레코드를 놓을 장소일 뿐입니다.

공인 CA와 사내 CA의 차이는 발급 능력이 아니라 신뢰 범위

CA가 되는 데 필요한 것은 개인키와 CA:TRUE인 인증서뿐이라, 조직이 자체 CA를 운영하는 것도 가능합니다. Let's Encrypt는 그중 Root 인증서가 브라우저·OS 신뢰 저장소에 등재된 공인 CA입니다.

공인 CA (acme) 사내 CA (ca)
Root의 위치 브라우저·OS 신뢰 저장소에 이미 있음 조직이 클라이언트에 직접 배포해야 함
도메인 소유권 검증 필요. CA가 신청자를 모른다 불필요. CA가 곧 조직 자신이다
발급 가능한 이름 인터넷에 등록된 도메인만 제약 없음

공인 CA가 발급한 인증서는 전 세계 클라이언트가 신뢰하므로, CA는 발급 전에 신청자가 그 도메인을 통제하는지 스스로 확인해야 합니다. 확인 통로는 인터넷에서 도달 가능한 경로뿐입니다. 그래서 *.local이나 server01.internal 같은 이름은 소유권 개념 자체가 없어 공인 CA의 발급이 금지되어 있습니다. 

apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: letsencrypt-prod
spec:
  acme:
    server: https://acme-v02.api.letsencrypt.org/directory
    email: admin@example.com
    privateKeySecretRef:
      name: letsencrypt-prod-account-key   # 계정 키. cert-manager가 생성해 저장
    solvers:
      - http01:
          ingress:
            ingressClassName: nginx

Certificate

apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: app-tls
spec:
  secretName: app-tls          # 결과물이 저장될 Secret 이름
  dnsNames:
    - app.example.com    # 인증서의 SAN
  issuerRef:
    name: letsencrypt-prod
    kind: ClusterIssuer
  duration: 2160h              # 요청할 유효기간(90일). CA가 거부할 수 있다
  renewBefore: 720h            # 만료 30일 전 갱신
SAN (Subject Alternative Name)

인증서가 유효한 도메인 목록을 담는 필드. 클라이언트는 접속하려는 호스트명이 이 목록에 있는지 확인하고, 없으면 연결을 거부합니다. 개별 도메인을 여러 개 나열하거나 *.example.com 같은 와일드카드를 쓸 수 있습니다. 과거에는 Subject의 CN 필드를 썼지만 현재 브라우저는 CN을 무시하고 SAN만 봅니다.

  • duration은 요청값입니다. 실제 유효기간은 CA가 결정합니다. Let's Encrypt는 90일로 발급합니다(2025년부터 6일짜리 단기 인증서도 선택 가능)
  • renewBefore를 지정하지 않으면 전체 수명의 2/3 시점에 갱신합니다

CertificateRequest, Order, Challenge

CertificateRequest

CSR을 담은 리소스. 개인키는 여기에 들어가지 않습니다.

Order

ACME 서버에 등록된 발급 주문. ACME 타입에서만 생성됩니다.

Challenge

도메인 하나당 하나씩 생성되는 소유권 검증 작업. 검증이 끝나면 삭제됩니다.

Certificate와 CertificateRequest의 차이

둘 다 "인증서를 발급해 달라"는 요청이지만 유효한 기간이 다릅니다.

Certificate CertificateRequest
성격 원하는 상태 선언 특정 CSR 하나에 대한 발급 요청
수명 지우기 전까지 유지 발급이 끝나면 역할 종료
갱신 포함. 만료가 가까우면 다시 발급 없음. 갱신하려면 새로 만들어야 함
CSR cert-manager가 만들어 준다 이미 만들어진 CSR을 담는다

차이를 만드는 것은 갱신입니다. Certificate를 한 번 선언해 두면 만료 시점마다 cert-manager가 새 CertificateRequest를 만들어 발급을 반복합니다. 리비전이 올라가 app-tls-1, app-tls-2 식으로 새 리소스가 생기고 이전 것은 기록으로 남습니다.

구조로 보면 Deployment와 ReplicaSet의 관계와 같습니다. 선언은 하나이고, 그 선언을 실행하는 하위 리소스는 변경이 있을 때마다 새로 만들어집니다.

CertificateRequest를 직접 만들 수도 있습니다. 이미 CSR을 갖고 있고 한 번만 발급받으면 되는 경우입니다. 다만 그러면 갱신은 직접 해야 합니다.

직접 작성하지 않으므로 명세보다는 조회 결과로 보는 편이 실제에 가깝습니다. 발급이 진행 중일 때의 모습입니다.

검증이 끝나면 Challenge와 Order는 사라지고 Certificate가 READY=True로 바뀝니다. 즉 이 리소스들은 발급이 멈췄을 때 어느 단계에서 멈췄는지를 확인하는 용도입니다.

중간 CA (Intermediate CA)

Root CA가 직접 서버 인증서를 서명하지 않고 중간에 두는 인증기관. Root의 개인키는 오프라인에 격리해 두고 실제 발급은 중간 CA가 담당합니다. 중간 CA가 뚫려도 해당 중간 CA만 무효화하면 되고 Root는 유지됩니다. 그래서 인증서는 서버 인증서 → 중간 CA → Root CA 형태의 체인을 이룹니다.

  • tls.key는 cert-manager가 발급 과정 1단계에서 만든 키이고, tls.crt 안의 공개키와 한 쌍이며, CSR에 서명할 때 쓴 키입니다. CA의 개인키는 CA 쪽에만 있고 이 Secret에 들어오지 않습니다. ca.crt도 CA의 인증서일 뿐 개인키가 아닙니다. 다만 ca Issuer가 참조하는 Secret은 사내 CA의 개인키를 담고 있는데, 그것은 발급 결과물인 이 Secret과 다른 리소스입니다
  • 개인키는 클러스터 안에서 생성되고 외부로 나가지 않습니다
  • tls.crt에 중간 CA가 함께 들어가는 이유는 클라이언트가 체인을 검증하려면 필요하기 때문입니다 (2-3에서 상세)
  • 갱신 시 같은 Secret의 내용이 교체됩니다. 이름은 바뀌지 않으므로 참조하는 쪽은 수정할 필요가 없습니다

tls.crt의 중간 CA와 ca.crt는 같은 것인가

역할이 다르고, 경우에 따라 같을 수도 다를 수도 있습니다.

tls.crt의 중간 CA ca.crt
목적 서버가 클라이언트에게 보낼 체인의 일부 클라이언트가 신뢰 앵커로 쓸 CA 인증서
쓰는 쪽 서버 (핸드셰이크 때 전송) 클라이언트 (검증 기준)
  • 공인 CA(ACME): ca.crt가 아예 없습니다. 클라이언트가 Root를 이미 갖고 있으므로 넣을 필요가 없고, 중간 CA는 tls.crt에만 들어갑니다
  • 사내 CA: 서명한 CA가 하나뿐이라면 그 인증서가 체인의 연결고리이자 신뢰 앵커 역할을 동시에 합니다. 사내 CA가 다시 상위 Root의 서명을 받은 중간 CA라면 서로 달라집니다

원칙이 하나 있습니다. Root는 tls.crt에 넣지 않습니다. 클라이언트가 이미 갖고 있어야만 검증이 성립하므로 보내봐야 의미가 없기 때문입니다(RFC 5246 §7.4.2). cert-manager도 의도적으로 제외합니다.

ingress-shim

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  annotations:
    cert-manager.io/cluster-issuer: letsencrypt-prod
spec:
  tls:
    - hosts:
        - app.example.com
      secretName: app-tls     # 이 이름으로 Certificate가 생성된다

선언 불필요

Certificate를 따로 쓰지 않아도 됩니다. 생성된 리소스는 kubectl get certificate로 그대로 보이고 이후 동작은 동일합니다.

생성 단위

Ingress가 아니라 spec.tls 항목입니다. 블록 세 개면 Certificate도 세 개. 한 블록에 hosts를 여러 개 넣으면 SAN이 여러 개인 인증서 하나가 만들어집니다.

삭제 동작

Ingress가 소유자로 기록되므로 Ingress를 지우면 Certificate도 삭제됩니다. 단 Secret은 기본적으로 남습니다.

한계: 어노테이션으로 지정할 수 있는 항목은 Issuer, 갱신 시점, 키 생성 방식 정도입니다. 와일드카드에 DNS-01 solver를 붙이거나 여러 Ingress가 하나의 인증서를 공유하는 구성은 Certificate를 직접 작성하는 편이 단순합니다.

1-4 · Issuance

발급 과정과 도메인 소유권 검증

Certificate가 만들어진 시점부터 Secret에 인증서가 들어가기까지.

관문

ACME 발급에서 실질적인 장벽은 서명이 아니라 도메인 소유권 검증입니다.

발급 흐름

1. 개인키 · CSR cert-manager가 클러스터 안에서 키를 만들고 CSR 작성
2. 발급 주체 분기 ca/selfSigned는 즉시 서명, acme는 검증 필요
3. 소유권 증명 HTTP-01 또는 DNS-01로 토큰 배치 후 CA가 확인
4. CSR 제출 검증 통과 후 서명된 인증서 수령
5. Secret 저장 Certificate가 READY=True
CSR (Certificate Signing Request)

CA에 제출하는 인증서 발급 신청서. 공개키와 신청 도메인(SAN)이 담기고 신청자의 개인키로 서명됩니다. 이 서명이 "이 공개키에 대응하는 개인키를 갖고 있다"는 증명이 됩니다. 개인키 자체는 들어가지 않고 CA에게 전달되지도 않습니다. 즉 CSR은 신청자가 서명한 요청서고, 인증서는 CA가 서명한 보증서입니다.

Secret이 만들어진 시점에서 cert-manager의 작업은 끝납니다. 이 Secret을 읽어 실제 TLS 연결에 사용하는 것은 Ingress Controller나 Gateway의 몫입니다.

도메인 소유권 검증

CA 입장에서 신청자가 누구인지는 확인하지 않습니다. 확인하는 것은 "이 도메인을 통제하고 있는가" 하나뿐입니다. 이 검증이 없으면 아무나 남의 도메인 인증서를 발급받을 수 있습니다.

HTTP-01

지정된 URL에 정해진 값을 응답해서 증명합니다. 해당 도메인의 웹 서버를 통제하고 있음을 보이는 방식입니다.

  • cert-manager가 검증 응답용 임시 Pod·Service·Ingress 생성
  • ACME 서버가 http://<도메인>/.well-known/acme-challenge/<토큰> 요청
  • 정해진 값을 응답하면 통과하고 임시 리소스는 정리됨
solvers:
  - http01:
      ingress:
        ingressClassName: nginx
  • 퍼블릭 DNS 해석 + 80 포트 인터넷 노출 필요
  • 와일드카드 발급 불가
  • HTTPS 리다이렉트는 ACME 서버가 따라가므로 동작. 다만 검증 경로가 인증이나 WAF에 막히면 실패

DNS-01

DNS TXT 레코드에 정해진 값을 등록해서 증명합니다. 도메인의 DNS를 통제하고 있음을 보이는 방식입니다.

  • cert-manager가 DNS 공급자 API로 _acme-challenge.<도메인> TXT 레코드 생성
  • ACME 서버가 그 레코드를 조회해 값을 확인
  • 통과하면 레코드는 삭제
solvers:
  - dns01:
      azureDNS:
        resourceGroupName: dns-rg
        hostedZoneName: example.com
        managedIdentity:
          clientID: <client-id>
  • DNS 공급자 API 자격 증명 필요
  • 서비스가 인터넷에 노출되지 않아도 발급 가능
  • 와일드카드는 이 방식으로만
TXT 레코드

DNS 레코드 타입 중 하나. A 레코드가 도메인을 IP로, CNAME이 다른 도메인으로 연결하는 것과 달리 TXT는 임의의 문자열을 담습니다. 이름 해석에는 쓰이지 않고, 도메인 소유자만 값을 넣을 수 있다는 성질을 이용해 검증 용도로 쓰입니다. SPF·DKIM 같은 메일 인증도 같은 방식입니다.

자격 증명과 권한 범위

존 전체에 대한 쓰기 권한이 필요합니다. cert-manager가 침해되면 그 존의 A 레코드까지 바꿀 수 있습니다. CNAME 위임으로 범위를 줄일 수 있습니다. 운영 존에는 _acme-challenge를 검증 전용 존으로 향하는 CNAME 하나만 고정으로 두고, cert-manager에는 그 전용 존 권한만 줍니다. ACME 서버는 TXT 조회 시 CNAME을 따라가므로 검증은 그대로 성립합니다.

내부 전용 서비스

CA가 조회하는 대상은 서비스가 아니라 DNS 존입니다. 루트부터 위임을 따라 내려가 권한 있는 네임서버에 질의합니다. 따라서 서비스가 사설 IP만 갖고 있거나 아직 배포되지 않아도 발급됩니다. 다만 존 자체는 인터넷에서 조회 가능해야 합니다.

와일드카드

*.example.com은 app.example.com에는 유효하지만 api.app.example.com에는 유효하지 않습니다. example.com 자체도 포함하지 않으므로 둘 다 필요하면 dnsNames에 나란히 적어야 하고, 이때 _acme-challenge.example.com에 서로 다른 TXT 값 두 개가 동시에 등록됩니다.

전파 지연

존 변경 반영과 리졸버 캐시 때문에 레코드 생성 직후에는 조회되지 않을 수 있습니다. DNS-01 발급이 HTTP-01보다 오래 걸리는 것은 정상입니다. 기존 TXT 레코드가 남아 있거나 존을 여러 곳에서 관리하면 계속 실패합니다.

self-check: cert-manager는 ACME 서버에 검증을 요청하기 전에 스스로 한 번 확인합니다. 토큰 경로가 응답하는지, TXT 레코드가 조회되는지를 먼저 보고 통과한 뒤에야 서버에 알립니다. 발급이 pending에서 오래 멈춰 있다면 대부분 이 self-check를 통과하지 못한 상태입니다.

갱신

  • 개인키를 다시 만들지는 privateKey.rotationPolicy로 정합니다. cert-manager v1.18부터 기본값이 Always로 바뀌어 갱신마다 새 키를 만듭니다(이전 버전은 Never)
  • 소유권 검증도 다시 수행합니다. 최초 발급 때 동작하던 solver 경로가 이후 막히면 갱신 시점에 실패합니다
  • Secret의 내용만 교체되고 이름은 유지됩니다. 다만 애플리케이션이 새 내용을 다시 읽는 것은 별개 문제입니다
1-5 · Boundary

cert-manager의 역할이 아닌 것

Certificate가 READY=True이고 Secret에 최신 인증서가 있으면 cert-manager 입장에서는 정상입니다. 그런데 사용자가 겪는 문제는 대부분 그 이후 구간에서 발생합니다.

왜 중요한가

경계를 알아두면 문제가 생겼을 때 어디를 봐야 할지가 정해집니다.

TLS 종료

cert-manager는 TLS 연결을 처리하지 않습니다. Secret을 읽어 인증서를 제시하고 암호화 연결을 수립하는 것은 Ingress Controller·Gateway·로드밸런서의 일입니다.

인증서가 정상인데 접속이 안 되면 spec.tls에 secretName이 빠졌는지, 네임스페이스가 다른지, 애초에 종료 지점이 앞단 LB라 클러스터 안 인증서를 아무도 안 쓰는지 봅니다. → 3-4

갱신된 인증서의 반영

Secret 내용은 교체하지만, 그것을 쓰는 앱이 다시 읽도록 만들지는 않습니다. 마운트된 파일은 kubelet이 갱신해 주지만 앱이 기동 시 한 번 읽고 메모리에 들고 있으면 옛 인증서를 계속 씁니다.

nginx-ingress처럼 감시해서 다시 읽는 구현체도 있고, 아니면 파드 재시작이나 리로드 로직, Reloader 같은 컨트롤러가 필요합니다. → 5장

Root CA의 신뢰 배포

사내 CA로 발급한 인증서는 클라이언트가 그 Root CA를 신뢰해야 검증됩니다. 컨테이너 이미지에 넣거나 ConfigMap으로 마운트하거나 OS 신뢰 저장소에 등록하는 일은 별도입니다.

공인 CA를 쓸 때 이 과정이 없는 이유는 Root가 이미 배포되어 있기 때문이지 cert-manager가 처리해서가 아닙니다.

mTLS 정책

클라이언트 인증서를 발급할 수는 있습니다. 하지만 서버가 그것을 요구할지, 어떤 CA까지 허용할지, 어떤 필드로 접근을 통제할지는 관여하지 않습니다. → 3-3

Secret 보호

개인키는 Secret에 평문(base64)으로 저장됩니다. RBAC 제한과 etcd 암호화는 클러스터 설정으로 따로 해야 하고, 개인키를 클러스터 밖에 두려면 Vault 같은 외부 Issuer로 갑니다.

구간 담당
인증서 발급·갱신 cert-manager
Secret → TLS 연결 Ingress Controller / Gateway / LB
갱신된 Secret 재로딩 애플리케이션 또는 별도 컨트롤러
Root CA 신뢰 배포 클라이언트 환경 구성
mTLS 검증 정책 메시 또는 애플리케이션
Secret 접근 통제 쿠버네티스 RBAC, etcd 암호화
여기서 나오는 질문 그런데 애초에 그 "인증서"라는 게 뭐고, 왜 CA라는 제3자가 끼어 있어야 하지?

지금까지는 cert-manager가 발급받아 오는 대상을 블랙박스로 다뤘습니다. 2장에서 그 안을 엽니다.

2-1 · Why CA

인증서와 인증기관의 등장 배경

암호화만으로는 부족합니다. 빠지는 것은 상대가 누구인가입니다.

공개키 암호가 푼 것

안전하지 않은 경로에서 통신에 쓸 키를 공유하는 문제. 남은 것은 신원 확인입니다.

남은 문제: 받은 공개키가 누구의 것인가

경로 중간의 누군가가 서버의 공개키를 가로채고 자기 공개키를 대신 내려보내면, 클라이언트는 그 사실을 알 수 없습니다. 클라이언트는 중간자의 공개키로 암호화하고, 중간자는 그것을 풀어 읽은 뒤 다시 서버의 공개키로 암호화해 전달합니다. 양쪽 모두 정상 통신 중이라고 믿습니다.

중간자 공격

서버 → 중간자서버 공개키 전송
중간자 → 클라이언트중간자 공개키를 "서버 것"이라고 전달
클라이언트 → 중간자중간자 공개키로 암호화한 데이터
중간자 → 서버복호화해서 읽은 뒤 서버 공개키로 재암호화

중간자 공격 — 메시지 순서

sequenceDiagram
    participant C as 클라이언트
    participant M as 중간자
    participant S as 서버

    S->>M: 서버 공개키
    M->>C: 중간자 공개키 (서버 것이라고 주장)
    C->>M: 중간자 공개키로 암호화한 데이터
    M->>M: 복호화해서 읽음
    M->>S: 서버 공개키로 다시 암호화
암호화는 정상 동작했지만 통신 상대가 달랐습니다. 공개키 암호는 기밀성은 제공하지만 상대의 신원은 보장하지 않습니다.

제3자의 보증

  • CA는 도메인 소유권을 확인한 뒤, 공개키와 도메인을 묶은 문서에 자신의 개인키로 서명합니다
  • 클라이언트는 CA의 공개키로 그 서명을 검증합니다. 유효하면 "CA가 보증한 내용"임이 확인됩니다
  • 중간자가 공개키를 바꿔치기해도 그 공개키에 대한 CA의 서명을 만들어낼 수 없습니다

1장에서 본 도메인 소유권 검증(HTTP-01, DNS-01)이 바로 CA가 서명하기 전에 수행하는 확인 절차입니다.

신뢰의 출발점

문제가 한 단계 옮겨갑니다. CA의 서명을 검증하려면 CA의 공개키가 필요한데, 그게 진짜인지는 또 어떻게 아는가. 이 연쇄를 끊는 방법은 하나뿐입니다. 신뢰할 대상을 미리 정해서 클라이언트에 심어 두는 것입니다. OS와 브라우저는 신뢰하는 CA 인증서를 신뢰 저장소(trust store)에 담아 배포합니다.

Root CA 인증서는 자기 자신이 서명합니다(self-signed). 검증할 상위가 없기 때문입니다. Root를 신뢰하는 근거는 암호학적 검증이 아니라 "이미 갖고 있다"는 사실입니다. 어떤 CA를 넣을지는 브라우저·OS 벤더의 루트 프로그램이 심사해서 결정합니다.

Root가 직접 서명하지 않는 이유

  • Root 개인키가 유출되면 그 Root를 신뢰하는 모든 인증서가 한꺼번에 무너집니다. 신뢰 저장소는 OS·브라우저 업데이트로만 갱신되므로 회수에 수년이 걸립니다
  • 그래서 Root 개인키는 네트워크에 연결되지 않은 장비에 격리해 두고 평소에는 쓰지 않습니다

인증서에 담긴 것

전부 볼 필요는 없고, 검증에 직접 쓰이거나 운영 중 문제가 되는 것 위주로 봅니다.

인증서란

"이 공개키는 이 도메인의 것"이라는 문장에 CA가 서명한 문서입니다.

항목 내용 왜 중요한가
Subject / SAN 이 인증서가 대표하는 이름 접속한 호스트명과 대조된다
Issuer 이 인증서를 서명한 CA 체인의 다음 단계를 찾는 기준
Validity 유효 시작·종료 시각 만료되면 연결이 거부된다
Public Key 서버의 공개키 인증서가 보증하는 실체
Basic Constraints CA 여부와 체인 깊이 제한 서버 인증서가 다른 인증서를 서명하지 못하게 막는다
Key Usage / EKU 이 키로 할 수 있는 일 용도가 맞지 않으면 거부된다
Signature 발급자의 서명 위조·변조 여부를 확인한다

Subject와 SAN

원래는 Subject의 CN에 도메인을 적었지만 CN은 값 하나만 담을 수 있었습니다. 그래서 확장 필드인 SAN이 도입됐고, Chrome은 2017년에 CN 기반 대조를 제거했습니다. SAN에 없으면 CN에 적혀 있어도 실패합니다. 도메인 외에 IP 주소나 이메일도 들어갈 수 있습니다.

Issuer

서버 인증서의 Issuer는 중간 CA의 Subject와 같고, 중간 CA의 Issuer는 Root CA의 Subject와 같습니다. 이 연결이 체인입니다. 이름만으로 찾으면 동명이인 문제가 생기므로 실제로는 AKI(Authority Key Identifier)와 SKI(Subject Key Identifier)로 키 단위 매칭을 합니다.

Validity

절대 시간으로 박혀 있고, 검증하는 쪽은 자신의 현재 시각과 비교합니다. 그래서 클라이언트의 시계가 틀리면 유효한 인증서도 거부됩니다. 시간 동기화가 안 된 기기나 컨테이너에서 나는 오류가 여기 해당합니다.

Basic Constraints

CA:TRUE이면 이 키로 다른 인증서를 서명할 수 있습니다. 이 필드가 없으면 서버 인증서를 하나 받은 사람이 다른 도메인의 인증서를 마음대로 만들 수 있고, 실제로 초기 브라우저들이 이를 검사하지 않아 발생한 취약점이 있었습니다. pathlen으로 아래 CA 단계 수도 제한합니다.

Key Usage와 EKU

Key Usage는 서명·키 암호화 같은 암호학적 연산 단위이고, EKU(Extended Key Usage)는 목적 단위입니다.

  • serverAuth: TLS 서버 인증서에 필요
  • clientAuth: mTLS의 클라이언트 인증서에 필요

용도가 맞지 않으면 인증서가 유효해도 거부됩니다. mTLS를 구성할 때 서버용 인증서를 클라이언트에 그대로 쓰면 여기서 걸립니다. 1장의 Certificate.spec.usages가 이 값을 지정합니다.

실제로 열어보기

$ openssl x509 -in tls.crt -noout -text
Certificate:
    Data:
        Serial Number: 04:9f:...:c1
        Issuer: C=US, O=Let's Encrypt, CN=R11          # 이 인증서를 서명한 중간 CA
        Validity
            Not Before: Jul 15 09:21:03 2026 GMT       # 90일 수명
            Not After : Oct 13 09:21:02 2026 GMT
        Subject: CN=app.example.com                    # 참고용. 검증에는 쓰이지 않는다
        Subject Public Key Info:
            Public Key Algorithm: rsaEncryption
                Public-Key: (2048 bit)
        X509v3 extensions:
            X509v3 Extended Key Usage:
                TLS Web Server Authentication          # serverAuth

                CA:FALSE                               # 다른 인증서를 서명할 수 없다
            X509v3 Authority Key Identifier:
                C5:CF:...:9A                           # 중간 CA의 SKI와 일치

Issuer:  ... CN=ISRG Root X1   # Root가 서명
Subject: ... CN=R11            # 서버 인증서의 Issuer와 일치
Basic Constraints: critical
    CA:TRUE, pathlen:0         # 아래에 CA를 더 둘 수 없음
Subject Key Identifier:
    C5:CF:...:9A               # 서버 인증서의 AKI와 일치

Root CA 인증서

Subject: ... CN=ISRG Root X1   # 동일 = self-signed

    CA:TRUE

신뢰 체인

클라이언트가 app.example.com에 접속했을 때 그 인증서를 어떻게 신뢰하게 되는가.

서명 = 해시 + 개인키

CA는 인증서 본문 전체의 해시를 자신의 개인키로 처리해 끝에 붙입니다. 공개키는 본문 안의 한 필드일 뿐입니다.

서명과 검증

  • 서명: CA가 인증서 본문 전체의 해시를 구하고, 그것을 자신의 개인키로 처리한 값을 붙인다
  • 검증: 클라이언트가 본문 해시를 다시 구하고, 붙어 있는 서명을 CA의 공개키로 풀어 나온 값과 비교한다

두 값이 같으면 본문이 변조되지 않았다는 것과 그 서명을 만든 주체가 해당 개인키를 갖고 있었다는 것이 동시에 확인됩니다. 여기서 필요한 상위 CA의 공개키는 상위 CA의 인증서 안에 들어 있고, 그래서 검증이 한 단계 위 인증서를 요구하며 체인이 됩니다.

검증 순서

1. 서버 인증서Issuer를 보고 중간 CA를 찾는다
2. 중간 CA 공개키로 검증서버 인증서의 서명 확인
3. Root 공개키로 검증중간 CA 인증서의 서명 확인
4. 신뢰 저장소 확인Root가 이미 들어 있는가 — 여기서 끝
Root는 서명을 검증하는 대상이 아닙니다. self-signed이므로 자기 서명을 자기 공개키로 검증하는 것은 아무것도 증명하지 못합니다. Root에 대해 확인하는 것은 "이미 내 신뢰 저장소에 들어 있는가" 하나뿐입니다.

서버가 보내야 하는 것

인증서 전송 여부 이유
서버 인증서 필수 검증 대상
중간 CA 인증서 필수 클라이언트가 갖고 있지 않다
Root CA 인증서 생략 클라이언트의 신뢰 저장소에 이미 있다

1장에서 본 Secret의 tls.crt에 서버 인증서와 중간 CA가 함께 들어 있는 이유가 이것입니다.

언제 전달되는가

서버 인증서와 동시에, 같은 메시지 안에서 전달됩니다. 검증이 끝난 뒤 추가로 받아오는 것이 아닙니다. TLS의 Certificate 메시지는 인증서 하나가 아니라 인증서 목록이기 때문입니다. 

Certificate
 ├─ [0] app.example.com 인증서   # leaf가 항상 첫 번째
 └─ [1] 중간 CA 인증서           # 바로 앞 인증서를 서명한 CA 순서로

체인 때문에 왕복이 늘지는 않습니다. 클라이언트는 목록을 한 번에 받은 뒤 로컬에서 체인을 검증합니다. 3-1의 1-RTT / 2-RTT 계산에 인증서 체인 때문에 추가되는 왕복은 없습니다. tls.crt 파일 하나에 leaf와 중간 CA를 이어붙여 두는 이유도 그 파일 내용이 그대로 이 목록이 되기 때문입니다.

예외는 바로 아래의 AIA fetching입니다. 서버가 중간 CA를 빼먹었을 때 클라이언트가 별도로 가져오는 경우인데, 이때만 추가 왕복이 생깁니다.

AIA (Authority Information Access)

이 인증서와 관련된 CA 정보를 어디서 얻을 수 있는지를 담은 확장 필드 하나입니다. 값은 { 접근 방법, 접근 위치 } 쌍의 목록이고, CA Issuers와 OCSP는 별도의 필드가 아니라 그 안에 들어가는 항목의 종류입니다. 

X509v3 Authority Information Access:          # 확장 필드 하나
    OCSP - URI:http://r11.o.lencr.org         # 항목 1
    CA Issuers - URI:http://r11.i.lencr.org/  # 항목 2
  • OCSP 응답 서버 주소는 인증서 안에 있습니다. 클라이언트가 어디에 물어봐야 할지를 발급 시점에 CA가 적어 넣습니다
  • 인증서마다 자기 AIA를 가지므로 중간 CA 인증서에도 자체 AIA가 있습니다
  • CRL 주소는 AIA가 아니라 별도 확장 필드(CRL Distribution Points)입니다
  • 이 주소를 따라가는 것은 의무가 아닙니다. 브라우저는 대체로 따라가지만(AIA fetching) 프로그래밍 언어의 기본 TLS 클라이언트는 대부분 따라가지 않습니다

중간 CA를 빠뜨리면 클라이언트마다 결과가 갈립니다. 중간 CA를 캐시했거나 AIA를 따라가는 클라이언트에서는 성공하고, 그렇지 않은 쪽에서는 실패합니다. "브라우저에서는 되는데 서버 간 호출에서만 실패한다"는 증상이 나오면 이것부터 봅니다.

언어 라이브러리가 AIA를 따라가지 않는 이유

  • 중간 CA 전송은 표준상 서버의 의무입니다. 클라이언트가 보완할 이유가 없습니다
  • 핸드셰이크 도중에 별도 HTTP 요청이 필요합니다. 지연이 생기고, 그 요청이 실패하면 연결도 실패합니다
  • 인증서에 적힌 임의의 URL로 요청을 보내게 됩니다. 내부망 클라이언트에는 SSRF에 가까운 위험이 됩니다
  • 네트워크 상태에 따라 같은 인증서의 검증 결과가 달라집니다

예외적으로 OS TLS 스택을 쓰는 클라이언트(Windows Schannel, macOS Security)는 AIA를 따라갑니다. 그래서 Windows에서 되던 코드가 Linux 컨테이너에서만 실패하기도 합니다.

서명 외에 확인하는 것

항목 확인 내용 어긋날 때
유효기간 현재 시각이 Validity 구간 안에 있는가 만료 또는 클라이언트 시계 오류
호스트명 접속한 이름이 SAN에 있는가 도메인 불일치
용도 EKU에 serverAuth가 있는가 용도가 다른 인증서
CA 여부 체인 중간 인증서가 CA:TRUE인가 서버 인증서가 CA 자리에 있음
폐기 발급 후 무효화되지 않았는가 폐기된 인증서

호스트명 대조는 인증서만으로 판단할 수 없습니다. 클라이언트가 어떤 이름으로 접속했는지를 알아야 하므로, 인증서 검증은 항상 "무엇에 접속했는가"와 함께 이뤄집니다. IP로 직접 접속하면 SAN에 그 IP가 없는 한 실패합니다.

폐기 확인 — 1장에서 미뤄둔 이야기

서버의 개인키가 유출되면 공격자는 그 키와 인증서를 그대로 들고 다른 서버에서 정상적인 HTTPS 서비스를 열 수 있습니다. 인증서 자체는 CA가 서명한 진짜라 클라이언트는 아무 이상을 발견하지 못합니다. 이미 배포된 파일이라 회수할 방법이 없으니, CA가 "이건 이제 무효"라고 별도로 알리는 수밖에 없습니다.

CRL

폐기된 인증서의 일련번호 목록을 파일로 공개합니다. CA 하나가 발급한 전체 목록이라 수 MB까지 커지고, 매번 받을 수 없어 캐시하게 됩니다. 그만큼 최신 상태가 아닙니다.

OCSP

인증서 하나의 상태만 CA 서버에 질의합니다. 응답은 작고 최신이지만 접속할 때마다 요청이 나가 느려지고, 사용자가 어떤 사이트에 접속하는지가 CA에 노출됩니다.

OCSP stapling

서버가 미리 받아둔 OCSP 응답을 핸드셰이크 때 함께 건네줍니다. CA 서명이 붙어 있어 위조할 수 없고, 클라이언트가 CA에 접속할 필요가 없어져 지연과 프라이버시 문제가 함께 해결됩니다.

그래도 남는 문제

CA 서버가 응답하지 않을 때 차단하면 CA 장애 한 번이 전체 장애가 되고, 통과시키면 폐기 확인이 없는 것과 같아집니다. 브라우저는 후자를 택했고, 그래서 공격자가 OCSP 요청만 막으면 폐기가 무력화됩니다.

결론: 확인 절차를 강제할 수 없다면 남은 방법은 인증서가 유효한 기간 자체를 줄이는 것입니다. 90일이면 피해 기간이 최대 90일, 47일이면 그만큼 더 짧아집니다. 1-2에서 본 유효기간 단축 일정의 근거가 여기 있습니다.

Let's Encrypt는 2025년 8월 6일 OCSP 응답 서버를 껐습니다. 다만 이쪽의 공식 이유는 "동작하지 않아서"가 아니라 프라이버시와 운영 단순화입니다.

여기서 나오는 질문 이 인증서를 실제로 주고받고 검증하는 절차는 어디서 일어나지? 그리고 왜 요즘은 TLS 1.3을 쓰라고 하지?

인증서는 TLS 안에서 쓰이는 재료이고, 그것을 주고받는 절차가 TLS 핸드셰이크입니다. 3장에서 봅니다.

3-1 · TLS 1.2 → 1.3

TLS의 동작과 버전 변화

TCP는 데이터를 그대로 실어 나릅니다. TLS는 그 위에 얹혀 기밀성·무결성·인증을 제공합니다.

SSL과 TLS

Netscape의 SSL이 IETF로 넘어가면서 TLS가 됐습니다. SSL 3.0의 다음 버전이 TLS 1.0입니다. "SSL 인증서"라는 표현이 남아 있지만 프로토콜은 모두 TLS입니다.

기밀성 제3자가 내용을 읽을 수 없다 대칭키 암호화
무결성 내용이 변조되면 감지된다 인증 태그
인증 상대가 주장하는 그 서버가 맞다 2장의 인증서

무결성은 데이터에 검증용 태그를 붙여 보장합니다. 받는 쪽이 같은 방식으로 다시 계산해 비교하고 다르면 연결을 끊습니다. 태그를 암호화와 별도로 계산하면 MAC, 한번에 처리하면 AEAD이고 TLS 1.3은 AEAD만 씁니다.

TLS 1.2의 핸드셰이크

RTT 34ms 가정. TCP 연결 68ms + TLS 핸드셰이크 136ms, 첫 응답까지 272ms. 출처: Wikimedia Commons
  1. 클라이언트가 지원하는 알고리즘 조합을 목록으로 전송
  2. 서버가 하나를 골라 알려주고 인증서와 키 교환 파라미터 전송
  3. 클라이언트가 인증서를 검증하고(2장) 자기 몫의 파라미터 전송
  4. 양쪽이 같은 대칭키를 계산하고 Finished로 상호 검증

암호화된 데이터를 보내기까지 왕복 2회가 필요합니다.

RTT (Round-Trip Time)

패킷이 상대에게 갔다가 돌아오는 데 걸리는 시간. 핸드셰이크 비용을 초 단위가 아니라 "왕복 몇 번"으로 세는 이유는 실제 소요 시간이 거리와 회선 상태에 따라 달라지기 때문입니다. 왕복 횟수는 프로토콜이 결정합니다.

cipher suite

TLS 연결 하나에는 서로 다른 종류의 알고리즘이 여러 개 필요합니다. 하나씩 따로 협상하면 맞지 않는 조합이 나올 수 있어서, 검증된 조합을 미리 묶어 이름을 붙여 두고 그중 하나를 고르는 방식을 씁니다. 이 묶음 하나가 cipher suite입니다.

서버 설정에서 "허용 cipher suite 목록"을 관리한다는 것은 이 후보 목록을 손보는 일입니다. TLS 1.2에는 수십 가지가 정의돼 있었고, 그중에는 오래된 클라이언트 호환을 위해 남겨둔 취약한 조합도 섞여 있었습니다.

키 교환 방식과 PFS

RSA 키 전송

클라이언트가 대칭키 재료를 만들어 서버 공개키로 암호화해 보내고, 서버가 개인키로 풉니다. 누군가 트래픽을 저장해 두었다가 나중에 서버 개인키를 손에 넣으면 과거 통신을 전부 복호화할 수 있습니다.

(EC)DHE

양쪽이 임시 키 쌍을 만들어 공개값만 교환하고 각자 계산으로 같은 값에 도달합니다. 대칭키가 네트워크를 지나가지 않고 임시 키는 매 연결마다 버려집니다. 개인키가 유출돼도 과거 트래픽은 안전합니다 — 전방향 안전성(PFS).

TLS 1.2의 문제

1. 느리다

핸드셰이크에 2 RTT. 지연이 큰 모바일에서 체감이 크고 연결이 많은 웹에서는 누적됩니다.

3. 다운그레이드 공격

협상 초반은 평문입니다. 중간자가 ClientHello의 지원 목록을 조작해 약한 조합만 남기면 양쪽은 그것이 최선이라고 믿습니다.

2. 취약한 선택지 잔존

협상 목록에 안전하지 않은 조합이 남아 있었습니다.

4. 인증서가 평문으로 오간다

Certificate 메시지가 암호화 전에 전송되어, 도청자는 인증서만 보고 접속 대상 사이트를 알 수 있습니다.

TLS 1.3의 핸드셰이크

같은 조건. TCP 68ms는 동일하지만 TLS 구간이 136ms → 68ms로 줄고 첫 요청 전송이 204ms → 136ms로 앞당겨집니다. 그림에는 생략됐지만 같은 구간에 EncryptedExtensions와 CertificateVerify도 함께 전송됩니다. 출처: Wikimedia Commons

1. 1-RTT로 단축

핵심은 클라이언트가 묻기 전에 미리 보내는 것입니다. ClientHello에 "아마 이 방식을 쓸 테니 내 값은 이것"이라며 key share를 함께 보냅니다. 서버는 ServerHello 시점에 이미 양쪽 값을 갖게 되어 그 자리에서 대칭키를 확정하고, 이후 인증서를 포함한 나머지는 전부 암호화되어 나갑니다. 왕복이 줄었고 동시에 4번 문제도 해결됐습니다.

추측이 틀리면 HelloRetryRequest로 한 번 더 왕복합니다. 최악의 경우가 TLS 1.2의 기본값과 같습니다.

2. 선택지 제거

RSA 키 전송·정적 DH(PFS 없음), CBC·RC4·3DES, SHA-1·MD5, TLS 압축, 재협상이 모두 삭제됐습니다. 그 결과 cipher suite가 5개로 줄고 구조도 바뀌었습니다. 

TLS_AES_128_GCM_SHA256
     └대칭암호┘ └해시┘

키 교환은 (EC)DHE로 고정되어 협상할 필요가 없어졌고 인증 방식은 별도 확장으로 협상합니다. PFS가 프로토콜의 전제가 됐습니다.

3. 다운그레이드 차단

CertificateVerify에서 서버가 핸드셰이크 메시지 전체(transcript)에 서명합니다. 중간자가 ClientHello를 조작했다면 양쪽이 기억하는 내용이 달라져 서명 검증이 실패합니다. 여기에 더해 1.2로 협상하게 된 경우 ServerHello 랜덤값 끝에 정해진 표식을 넣어 클라이언트가 강제된 다운그레이드를 판단할 수 있게 합니다.

4. 0-RTT (선택)

이전에 연결한 적 있는 서버라면 첫 패킷에 데이터를 실어 보낼 수 있습니다. 다만 재전송 공격에 취약해서, 공격자가 그 패킷을 복사해 여러 번 보내면 서버가 같은 요청을 반복 처리할 수 있습니다. 반복해도 문제없는 요청에만 씁니다.

그것을 걸러내는 것이 바로 다음에 오는 Certificate와 CertificateVerify입니다. 중간자는 그 인증서에 대응하는 개인키가 없어 서명을 만들 수 없고, 검증이 실패해 연결이 끊깁니다. 2-1의 중간자 공격이 여기서 차단됩니다.

여기서 나오는 질문 인증서가 암호화됐다면, 서버는 어떻게 어느 인증서를 보낼지 알지?

TLS 1.3이 여전히 평문으로 남겨둔 값이 하나 있습니다. 그 값이 SNI입니다.

3-2 · SNI

SNI

하나의 IP에 여러 도메인을 올리려면, 서버가 인증서를 고르기 전에 클라이언트가 어디를 찾는지 알아야 합니다.

순서 문제

Host 헤더는 암호화된 통로 안에 있고, 그 통로를 만들려면 먼저 인증서를 골라야 합니다.

1. TCP 연결
2. TLS 핸드셰이크서버가 인증서를 보내야 한다
3. HTTP 요청Host 헤더가 여기 있다

그래서 과거에는 HTTPS 사이트마다 전용 IP가 필요했습니다. SNI(Server Name Indication)는 클라이언트가 핸드셰이크의 첫 메시지에 접속하려는 호스트명을 넣어 보내는 TLS 확장입니다(RFC 6066).

SNI 기반 인증서 선택

ClientHelloserver_name = app.example.com
서버SNI를 보고 맞는 인증서 선택
ServerHello + Certificate고른 인증서 전송
GET /Host: app.example.com

쿠버네티스에서의 의미

1장에서 spec.tls 블록마다 Secret이 하나씩 생긴다고 했습니다. 그 Secret들을 Ingress Controller가 메모리에 올려두고 들어오는 연결의 SNI를 보고 그중 하나를 고릅니다. 파드 하나, IP 하나로 여러 도메인을 처리하는 구조가 SNI 위에 서 있습니다.

SNI를 보내지 않은 경우

IP로 직접 접속하면 SNI가 비어 있습니다. 서버는 판단 근거가 없어 기본 인증서를 내놓습니다. nginx Ingress에서 Kubernetes Ingress Controller Fake Certificate가 보이는 상황이 이것입니다. 클라이언트는 SAN 불일치로 거부하는데, 인증서가 잘못 발급된 게 아니라 서버가 다른 인증서를 골랐기 때문입니다.

SNI와 Host 헤더가 다른 경우

둘은 다른 계층의 값이라 일치할 의무가 없습니다. curl --resolve나 -H "Host: ..."로 테스트할 때 갈릴 수 있습니다. 인증서는 SNI 기준, 라우팅은 Host 헤더 기준이라 A 도메인의 인증서로 연결하고 B의 백엔드로 라우팅되는 상황이 됩니다.

SNI는 평문이다

구조상 그럴 수밖에 없습니다. 암호화하려면 키가 필요한데, 키를 합의하려면 서버가 인증서를 골라야 하고, 그러려면 SNI가 먼저 읽혀야 합니다. 그래서 도청자는 내용은 몰라도 사용자가 어느 사이트에 접속했는지는 알 수 있습니다. 이 성질은 국가 단위 검열이나 기업 방화벽의 도메인 차단에 실제로 활용됩니다.

ECH (Encrypted Client Hello): 서버가 공개키를 DNS 레코드에 공개해 두면 클라이언트가 그 키로 ClientHello 자체를 암호화해 보냅니다. 다만 공개키를 미리 받을 경로(암호화된 DNS)가 필요하고 도입률도 제한적이라, 현재 운영 환경에서는 SNI가 노출된다고 보는 것이 맞습니다.

값 계층 암호화 쓰이는 곳
SNI TLS 핸드셰이크 평문 인증서 선택, TLS passthrough 라우팅
Host 헤더 HTTP 요청 암호화됨 L7 라우팅

평문이라는 점은 프라이버시 측면에서는 단점이지만, 인프라 관점에서는 복호화 없이도 라우팅할 수 있다는 뜻이 됩니다. 3-4의 passthrough 구성을 가능하게 하는 근거입니다.

3-3 · mTLS

mTLS

지금까지의 TLS는 한쪽만 확인합니다. 서버는 접속해 온 상대가 누구인지 모릅니다.

전제의 붕괴

"내부망에 들어와 있다면 신뢰할 수 있다"는 가정이 더 이상 성립하지 않게 됐습니다.

배경

공개된 웹사이트라면 서버 인증만으로 충분합니다. 문제는 내부 서비스입니다. 결제 서비스가 주문 서비스의 호출만 받아야 한다면 서버도 상대를 확인해야 합니다. 전통적으로 이 확인은 애플리케이션 계층(API 키, 토큰)에서 했고, 다음 문제가 따라옵니다.

  • 자격 증명이 요청 안에 담겨 전달됩니다. 유출되면 그대로 재사용됩니다
  • 서비스마다 인증 방식이 다릅니다(헤더, 쿼리 파라미터 등)
  • 인증이 애플리케이션 코드에 있어, 앱이 처리하기 전 단계에서는 아무 검증도 없습니다
mTLS는 이 확인을 전송 계층으로 내립니다. 연결이 수립되는 시점에 양쪽이 서로 인증서를 제시하고 검증하므로, 애플리케이션 코드가 실행되기 전에 신원 확인이 끝납니다.

동작 — 메시지 세 개가 추가된다

CertificateRequest

서버가 "너도 인증서를 내라"고 요구합니다. 이 메시지가 없으면 일반 TLS입니다.

Certificate

클라이언트가 자기 인증서를 보냅니다.

CertificateVerify

클라이언트가 핸드셰이크 내용에 자기 개인키로 서명합니다. 인증서만 보내면 남의 인증서를 복사해 쓸 수 있으므로, 개인키를 갖고 있음을 증명하는 단계가 필요합니다.

mTLS 핸드셰이크 — 메시지 순서

sequenceDiagram
    participant C as 클라이언트
    participant S as 서버

    C->>S: ClientHello
    S->>C: ServerHello + Certificate (서버 인증서)
    S->>C: CertificateRequest (클라이언트 인증서 요구)
    Note over C: 서버 인증서 검증
    C->>S: Certificate (클라이언트 인증서)
    C->>S: CertificateVerify (개인키로 핸드셰이크에 서명)
    Note over S: CA 번들로 클라이언트 인증서 검증
    Note over C,S: 양방향 인증 완료
CertificateRequest가 없으면 일반 TLS입니다. 나머지 흐름은 3-1에서 본 것과 동일합니다.
Phase 2의 demand client certificate와 Phase 3의 client certificate, 개인키 서명 단계가 mTLS로 추가되는 부분입니다. 이 그림은 TLS 1.2 + RSA 키 전송 기준이라 pre-master-secret 흐름이 나오지만, 여기서는 클라이언트 인증서가 오가는 위치만 보면 됩니다. 출처: Wikimedia Commons

서버 인증과의 비대칭

같은 인증서 검증이지만 한 가지가 다릅니다. 대조할 이름이 없다는 것입니다. 서버 인증서는 "접속한 호스트명이 SAN에 있는가"로 판단하지만, 서버 입장에서 "이 클라이언트는 이런 이름이어야 한다"를 미리 알 수 없습니다.

단계 확인 내용 담당
인증 신뢰하는 CA가 서명한 유효한 인증서인가 TLS 계층
인가 이 신원에게 이 작업을 허용할 것인가 애플리케이션 또는 프록시

클라이언트 인증서는 사내 CA로 발급해야 합니다. 공인 CA로 발급하면 그 CA가 서명한 인증서는 세상에 무수히 많으므로 첫 단계에서 걸러지는 것이 사실상 없습니다. 2장에서 본 사내 CA의 용도가 여기입니다.

쿠버네티스에서

cert-manager로 클라이언트 인증서 발급

apiVersion: cert-manager.io/v1
kind: Certificate
spec:
  secretName: order-client-tls
  commonName: order-service
  usages:
    - client auth   # EKU에 clientAuth
  issuerRef:
    name: internal-ca
    kind: ClusterIssuer

서버 쪽 검증 설정 (nginx Ingress)

annotations:
  nginx.ingress.kubernetes.io/auth-tls-secret: "default/internal-ca-bundle"
  nginx.ingress.kubernetes.io/auth-tls-verify-client: "on"

cert-manager는 인증서를 공급할 뿐, 어떤 인증서를 허용할지는 여기서 정합니다.

서비스 메시를 쓰는 경우

Istio나 Linkerd를 쓰면 사이드카가 파드마다 인증서를 받아 오고 짧은 주기로 회전시키며 서비스 간 통신을 자동으로 mTLS로 감쌉니다. 신원은 도메인이 아니라 워크로드 단위로 표현되고, SPIFFE ID 형식이 인증서의 SAN에 URI로 들어갑니다. 

spiffe://cluster.local/ns/payment/sa/payment-service

네임스페이스와 서비스 어카운트가 그대로 신원이 됩니다. 다만 발급 주체가 메시 자체의 CA이므로 cert-manager와 역할이 겹치고, 메시 환경에서 cert-manager는 주로 외부 노출 구간의 공인 인증서를 담당합니다.

운영상 주의점

관리 대상이 두 배

서버 인증서만 갱신하면 되던 것이 클라이언트 인증서까지 늘어납니다. 자동화 없이는 유지되지 않습니다.

CA 교체 순서

① 서버 CA 번들에 새 CA 추가 → ② 클라이언트 인증서를 새 CA 발급본으로 교체 → ③ 모두 넘어간 뒤 옛 CA 제거. 순서를 지키지 않으면 연결이 끊깁니다.

종료 지점과의 관계

앞단 LB에서 TLS를 종료하면 mTLS 검증도 거기서 끝나고, 뒤의 앱은 클라이언트가 누구였는지 모릅니다. 헤더로 전달해야 하고, 그 헤더를 외부에서 위조할 수 없게 막아야 합니다.

여기서 나오는 질문 그래서 복호화는 어디서 하고, 인증서는 어디에 둬야 하지?

mTLS를 어디서 처리할지는 TLS를 어디서 종료할지와 같은 문제입니다.

3-4 · Termination

TLS 종료 지점

클라이언트에서 파드까지 흐르는 동안 암호화를 어느 지점에서 푸느냐. 이 결정 하나로 인증서를 어디에 둘지와 어떤 기능을 쓸 수 있는지가 함께 정해집니다.

1~3장에서 유일한 결정 항목

앞의 내용은 이해, 여기는 선택입니다.

세 가지 방식

Edge 종료클라이언트 —HTTPS→ LB/Ingress —HTTP→ 파드
Re-encrypt클라이언트 —HTTPS→ LB/Ingress —HTTPS→ 파드
Passthrough클라이언트 —HTTPS→ LB(그대로 전달) → 파드가 종료
방식 복호화 지점 백엔드 구간 인증서가 필요한 곳
Edge 종료 LB·Ingress 평문 LB·Ingress
Re-encrypt LB·Ingress에서 한 번, 파드에서 다시 암호화 LB·Ingress + 파드
Passthrough 파드 암호화 파드

Secret을 누가 소비하는가

  • Edge 종료: Ingress Controller가 읽습니다. Certificate는 Ingress와 같은 네임스페이스에 있어야 합니다
  • Re-encrypt: 앞단은 공인 인증서, 백엔드는 사내 CA 인증서를 쓰는 것이 일반적입니다. 따라서 Certificate 리소스를 두 개 만들어야 하고, 하나는 Ingress가 다른 하나는 파드가 소비합니다
  • Passthrough: 파드가 직접 읽습니다. 1-5에서 본 갱신된 인증서를 앱이 다시 읽어야 하는 문제가 여기서 가장 두드러집니다

Passthrough의 제약: 복호화하지 않으므로 SNI 말고는 아무것도 볼 수 없습니다. 경로 기반 라우팅, 헤더 추가, 쿠키 기반 세션 고정, WAF, HTTP 접근 로그가 모두 불가능합니다. 종단 간 암호화가 요구되거나 파드가 직접 mTLS를 처리해야 할 때 선택합니다.

mTLS와의 관계

  • Edge 종료·Re-encrypt: LB·Ingress가 검증하고 결과를 헤더로 백엔드에 전달
  • Passthrough: 파드가 직접 검증. 클라이언트의 신원이 애플리케이션까지 그대로 도달
  • 서비스 메시 환경이라면 앞단은 Edge 종료로 두고 메시 구간을 mTLS로 감싸는 조합이 흔합니다
여기서 나오는 질문 그럼 실제로 인증서를 무료로, 자동으로 내주는 곳은 어디고 어떻게 그게 가능해졌지?

4 · Let's Encrypt / nip.io

Let's Encrypt와 nip.io

앞에서 설명한 구조 안에서 각각이 어느 자리를 차지하는지만 봅니다.

위치

Let's Encrypt = 2장의 인증기관이자 1장 Issuer의 대상. nip.io = 2장의 SAN에 들어갈 도메인을 확보하는 수단.

Let's Encrypt

비영리 인증기관입니다. ISRG(Internet Security Research Group)라는 재단이 운영하고 Mozilla·EFF·Akamai·Cisco 등이 후원합니다. 2015년 베타를 시작해 2016년 정식 서비스에 들어갔습니다. 2장의 구분으로 보면 공인 CA이고, Root 인증서(ISRG Root X1)가 신뢰 저장소에 등재되어 있습니다.

등장 배경

비용

인증서는 유료였습니다. 도메인 하나에 연 단위 비용이 들었고 와일드카드는 더 비쌌습니다.

수동 절차

CSR 제출, 소유권 확인 메일, 파일 내려받아 서버에 올리기를 사람이 했습니다.

수동 갱신

1~2년마다 같은 과정을 반복해야 했습니다.

2013년 대규모 감청 폭로 이후 "전 구간 암호화"가 기본이어야 한다는 인식이 더해졌지만, 비용과 절차가 남아 있는 한 개인 사이트나 소규모 서비스는 넘어오기 어려웠습니다.

순서로 보면 Let's Encrypt가 먼저고(2015), 브라우저가 HTTP 사이트에 "안전하지 않음" 표시를 붙이기 시작한 것은 그 뒤입니다(Chrome은 2017년 입력 필드부터, 2018년 모든 HTTP 페이지로 확대). 무료·자동 발급 수단이 먼저 생기면서 전면 HTTPS를 요구할 수 있는 조건이 만들어진 것입니다.

무엇을 했는가

1. 무료 발급

비용 장벽이 사라졌습니다. 다만 이것만으로는 부족했습니다. 사람이 붙어야 하는 절차가 남아 있었습니다.

2. 발급 절차를 API로

ACME 프로토콜을 만들어 사람이 개입하던 자리를 전부 프로그램이 처리하도록 바꿨습니다. 1장의 흐름(계정 등록 → 주문 → 소유권 증명 → CSR 제출 → 수령)이 모두 HTTP API입니다. cert-manager가 존재할 수 있는 이유가 여기 있습니다. ACME는 RFC 8555로 표준화됐고 다른 상용 CA도 채택했습니다.

3. 수명을 90일로

일부러 짧게 잡아 자동 갱신을 강제했습니다. 자동화가 제대로 동작하는지 90일마다 확인되는 구조이기도 합니다. 2장의 폐기 한계와 같은 방향이고, 2025년부터는 6일짜리 단기 인증서와 IP 주소 인증서도 선택할 수 있습니다.

무엇을 보증하는가

도메인 통제권만 확인합니다(DV). 신청자가 어떤 조직인지는 보지 않습니다. 그래서 피싱 사이트도 발급받을 수 있다는 지적이 있지만, 이는 DV 인증서 전반의 성격입니다. 인증서가 보증하는 것은 "지금 연결된 상대가 이 도메인의 통제권자가 맞다"이지 "이 사이트가 정직하다"가 아닙니다. 조직 실체를 확인하는 OV·EV는 서류 심사가 필요해 자동화할 수 없으므로 발급하지 않습니다.

운영 적용 전에는 staging 엔드포인트를 먼저 씁니다. 절차는 동일하지만 신뢰되지 않는 테스트용 CA가 서명하고 발급 횟수 제한이 느슨합니다. 실제 엔드포인트에는 도메인당 발급 횟수 제한이 있어 설정을 시행착오로 맞추다 보면 한도에 걸립니다.

nip.io

와일드카드 DNS 서비스입니다. <IP>.nip.io 형태의 이름을 질의하면 그 IP를 그대로 응답합니다. 등록도 설정도 없고, 이름 안에 IP가 들어 있어 DNS 서버가 파싱해서 돌려줍니다. 

10.0.0.1.nip.io        → 10.0.0.1
app.10.0.0.1.nip.io    → 10.0.0.1
api.10.0.0.1.nip.io    → 10.0.0.1

왜 필요한가

도메인을 사려면 비용과 시간이 들고, hosts 파일 수정은 그 장비에서만 동작하며 와일드카드도 안 됩니다. 무엇보다 공인 인증서를 받으려면 외부에서 조회되는 도메인이어야 합니다.

어떤 역할을 하는가

nip.io는 실제로 등록된 퍼블릭 도메인이라 Let's Encrypt가 검증할 수 있습니다. 퍼블릭 IP 하나만 있으면 도메인 등록 없이 공인 인증서를 붙일 수 있고, 앞에 아무 이름이나 붙일 수 있어 Ingress 호스트 규칙이나 3-2의 SNI 기반 인증서 선택을 하나의 IP에서 확인할 수 있습니다.

한계: 공용 서비스라 가용성이 남의 인프라에 달려 있고, 이름에 IP가 노출됩니다. *.nip.io에 대한 DNS 레코드를 만들 권한이 없으므로 와일드카드 인증서와 DNS-01 검증은 불가능합니다. 운영 환경에는 쓰지 않습니다. 같은 방식의 sslip.io가 대안 입니다.

둘을 합치면

실습 환경의 최소 조건

1. 퍼블릭 IPIngress 하나
2. nip.io 도메인DNS 설정 불필요

4. HTTP-01그 IP의 80 포트로 검증
5. 공인 인증서브라우저에 자물쇠

도메인 구매, DNS 설정, 인증서 비용 중 어느 것도 필요하지 않습니다.

여기서 나오는 질문 여기까지 다 갖춰 놓으면 문제가 안 생기나?

만료일은 인증서 안에 정확히 박혀 있었습니다. 아무도 그것을 보지 않았을 뿐입니다. 이 인증서는 웹 서버 TLS 인증서가 아니라 패킷 코어 소프트웨어 내부에서 쓰이던 인증서였고, 벤더가 제품에 담아 납품해 통신사 운영팀의 인증서 관리 목록에는 존재하지 않았습니다.

인증서 문제는 웹 서버에만 생기지 않습니다. 내부 구성 요소끼리 TLS를 쓰는 곳이라면 어디든 같은 일이 생길 수 있습니다.

5-2. 중간 CA 누락 — 클라이언트마다 결과가 다르다

클라이언트 결과 이유
Chrome, Safari 성공 중간 CA를 캐시했거나 AIA를 따라감
Firefox 성공 자주 쓰이는 중간 CA를 내장
curl (Windows/macOS) 성공 OS TLS 스택이 AIA를 따라감
curl (Linux) 실패 OpenSSL은 AIA를 따라가지 않음
Go / Java / Python 실패 자체 검증 로직, AIA 미지원

브라우저로 확인하고 배포했다가 서버 간 연동에서 터지는 전형적인 경로입니다. 

$ openssl s_client -connect app.example.com:443 -servername app.example.com
...
Certificate chain
 0 s:CN=app.example.com
   i:C=US, O=Let's Encrypt, CN=R11
 1 s:C=US, O=Let's Encrypt, CN=R11        # 이 줄이 없으면 중간 CA 누락
   i:C=US, O=Internet Security Research Group, CN=ISRG Root X1

cert-manager를 쓰면 tls.crt에 중간 CA가 함께 들어가므로 대개 문제가 없습니다. 인증서를 수동으로 넣거나 로드밸런서에 파일을 따로 업로드하는 구성에서 주로 발생합니다.

5-3. Secret은 갱신됐는데 앱이 옛 인증서를 서빙

확인 대상 상태
kubectl get certificate READY=True ✅
Secret의 tls.crt 최신 인증서 ✅
파드에 마운트된 파일 최신 인증서 ✅
실제 응답하는 인증서 만료된 옛 인증서 ❌

마운트된 파일은 kubelet이 갱신해 주지만, 앱이 기동 시 한 번 읽고 메모리에 들고 있으면 그 값은 바뀌지 않습니다. 문제는 아무도 오류를 내지 않는다는 점입니다. 모니터링이 Certificate나 Secret만 보고 있으면 감지하지 못하고, 만료일이 되어야 드러납니다.

Wrap-up

정리

한 문장으로: cert-manager가 담당하는 구간은 인증서 수명 주기에서 가장 좁은 부분이고, 장애는 대부분 그 바깥에서 납니다.

1. cert-manager

선언 → 수렴. Issuer와 Certificate만 작성하면 나머지는 컨트롤러가 처리하고 결과는 Secret입니다. 담당은 발급과 갱신까지.

2. 인증서와 CA

인증서는 "이 공개키는 이 도메인의 것"에 CA가 서명한 문서. 체인 검증은 신뢰 저장소에 도달하는 순간 끝납니다. 폐기가 잘 안 되니 수명이 짧아지는 중입니다.

3. TLS

1.3은 1-RTT·PFS 강제·인증서 암호화. 남은 평문은 SNI이고, 그 덕에 복호화 없는 라우팅이 가능합니다. 종료 지점이 유일한 결정 항목입니다.

4. Let's Encrypt

무료화보다 ACME로 절차를 API화한 것이 더 큽니다. 90일 수명은 자동 갱신을 강제하기 위한 선택입니다.

5. 장애

발급 실패가 아니라 추적 주체의 부재. 관리 목록에 없는 인증서, 체인 누락, 앱의 재로딩 누락.

운영에서 볼 것

리소스 상태가 아니라 실제 엔드포인트가 응답하는 인증서를 감시합니다. 갱신 실패를 알아차릴 경로를 따로 만듭니다.
